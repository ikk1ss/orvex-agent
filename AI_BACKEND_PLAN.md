# ORVEX Agent: план AI-бэкенда

Этот документ фиксирует решения из отдельного проекта ORVEX AI, которые подходят архитектуре ORVEX Agent. Это план реализации, а не описание уже работающих функций.

## Текущая архитектура ORVEX Agent

- Клиент: Telegram Mini App на HTML, CSS и JavaScript.
- Хостинг и серверные API: Vercel.
- Хранение профиля и персональной памяти: Supabase.
- Авторизация: проверка подписанного Telegram initData на сервере.
- AI-запросы и запуск агентов пока не реализованы.

Не переносить в этот проект Termux runtime, SQLite, Telegram-бота с polling, платёжную систему или локальный файл секретов.

## Что заимствуем из ORVEX AI

### 1. Единый AI Gateway

Сделать серверный модуль, который принимает унифицированный запрос и обращается к выбранному провайдеру. Клиент Mini App не должен обращаться к AI-провайдерам напрямую.

Ответ Gateway должен иметь единый формат:
- текст ответа;
- фактически использованные входные и выходные токены, если провайдер их сообщает;
- идентификатор выбранной модели и провайдера;
- длительность запроса;
- признак использования резервной модели;
- нормализованная ошибка, если запрос не выполнен.

Провайдера и набор моделей выбрать отдельно перед реализацией AI-чата. Не фиксировать их этим документом.

### 2. Серверный каталог моделей

Хранить каталог на серверной стороне. Для каждой модели предусмотреть:
- внутренний стабильный ID;
- отображаемое название;
- провайдера и upstream ID;
- краткое описание подходящих задач;
- ограничения контекста и генерации, если они подтверждены;
- доступность и статус проверки;
- порядок отображения.

Не показывать модель как доступную, пока её вызов не проверен. Цены и доступность провайдеров могут меняться, поэтому статические значения нельзя выдавать за актуальные.

### 3. Повторы и резервные модели

Повторять запрос только при временных сбоях: сетевой ошибке, таймауте, HTTP 429 или 5xx. Не повторять автоматически ошибки авторизации, некорректный запрос и другие постоянные ошибки.

Резервную модель использовать только если она заранее разрешена для данного сценария и поддерживает нужные возможности. Если модель была заменена, сообщить об этом пользователю. Не выполнять скрытое переключение, которое меняет ожидаемое качество или поведение ответа.

Для повторов использовать ограниченное число попыток, общий дедлайн запроса и короткую экспоненциальную задержку. Не допускать бесконечных повторов.

### 4. Применение настроек профиля и памяти

После подключения AI-чата сервер должен получать настройки профиля из проверенного серверного профиля, а не доверять значениям, присланным клиентом.

Применять:
- язык ответа;
- длину ответа;
- тон;
- формат;
- дополнительные инструкции;
- релевантные записи персональной памяти.

Не добавлять всю память без разбора. Выбирать только записи, относящиеся к текущему запросу. Ограничивать общий объём контекста и не позволять пользовательским инструкциям отменять системные правила безопасности.

До реализации этого механизма поля профиля остаются настройками хранения и не должны описываться как уже влияющие на ответы.

### 5. Учёт использования и диагностика

Сохранять минимальную техническую статистику:
- пользовательский ID из проверенной Telegram-сессии;
- провайдер и модель;
- количество входных и выходных токенов, если доступно;
- длительность;
- результат или тип ошибки;
- факт переключения на резервную модель.

Не записывать API-ключи, полное содержимое приватных запросов и ответов в технические логи. Доступ к пользовательской истории должен проверяться по Telegram ID на сервере.

На первом этапе это аналитика и диагностика, а не платёжный баланс и не списание кредитов.

### 6. Ограничение нагрузки

Не использовать только in-memory rate limiter: Vercel запускает отдельные serverless-инстансы, и их память не является общим хранилищем.

Лимиты запросов и параллельности реализовать с общим серверным хранилищем или атомарными операциями в Supabase. Определить лимиты отдельно для пользователя и для системы. Возвращать понятный ответ при превышении лимита.

## Этапы внедрения

1. Спроектировать контракт AI Gateway и серверный каталог моделей.
2. Выбрать провайдера и проверить реальные модели, ограничения и стоимость.
3. Реализовать один рабочий AI-запрос через серверный API, не раскрывая секреты клиенту.
4. Подключить настройки профиля и релевантную персональную память.
5. Добавить таймауты, ограниченные повторы, обработку ошибок и прозрачный fallback.
6. Добавить учёт токенов, времени ответа и ошибок.
7. Реализовать общий rate limiting и тесты на параллельные запросы.
8. Только после этого подключать дополнительные провайдеры и расширенные сценарии агентов.

## Обязательные проверки перед публикацией

- Подпись Telegram initData проверяется на сервере для каждого приватного API.
- Нельзя получить чужой профиль, историю или память, подменив ID в запросе.
- Секреты провайдеров находятся только в переменных окружения Vercel.
- Ошибки провайдера не раскрывают секреты и внутренние заголовки.
- Повторы ограничены и не создают дублирующиеся операции.
- Fallback явно отражается в результате.
- Пустой, слишком длинный или некорректный запрос отклоняется до обращения к провайдеру.
- Тесты проверяют успешный ответ, таймаут, 429, 5xx, неверный ключ, пустой ответ, fallback и параллельную нагрузку.
- Отдельно проверяются сборка Vercel и ручной запуск Mini App в Telegram.

## Граница текущей реализации

Документ не добавляет AI-вызовы, каталог активных моделей, биллинг или новые пользовательские обещания. Эти функции считаются реализованными только после появления кода, автоматических проверок и проверки в рабочем окружении.
